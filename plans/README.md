# Implementation Plans

Generated by the improve skill on 2026-06-28 (advisor pass against commit `fdbc18f`).

Implementation plans for the GemSpot monorepo (`web/` React frontend + `api/` Spring Boot
service). Plan 001 was docs-only; everything since changes source. Each executor: read the
plan fully before starting, honor its STOP conditions, run every Verify command, and update
the table below.

Executor rules:
- Read the whole plan before touching anything.
- Run the **Drift check** first. STOP on mismatch — plans were written against an older
  commit and the cited code may have moved.
- Never reproduce secret values — reference `file:line` + the key name only.
- `docs/service-context/*` is generated: only edit inside the
  `<!-- service-context:auto:start -->` … `<!-- service-context:auto:end -->` markers, and
  preserve human prose around them.
- Both deploys are gated on lint + tests (plan 004). Green suites before you open a PR, and
  rebase on master first — a branch behind master can fail the gate on the merged tree.
- Move the plan into `done/` and update the table when it lands.

## Findings considered and rejected

- **JWT tokens in `localStorage`** (`web/src/shared/store/authStore.ts`): deliberate SPA choice
  (15m access TTL + server-side refresh-reuse detection). Known trade-off, documented in
  `OBSERVABILITY.md`. Not a bug. See Direction options.
- **`/auth/email/verify` public**: by design — the UUID token *is* the authority. Not a finding.
- **OAuth tokens verified via outbound RestClient to Google/Facebook** (`AuthService.java`):
  standard provider verification, not SSRF. Not a finding.
- **`rejectSubmission()` lacks `@Transactional`** (`AdminService.java:173`) while
  `approveSubmission()` has it: **rejected** — reject is a single `save()` (already transactional
  at the repository boundary); the asymmetry is necessary (approve is multi-write), not a defect.
- **Mutable non-volatile `RestClient` field** (`AuthService.java:50`): the setter is a
  test-only seam and `RestClient` is thread-safe; no realistic production race. Rejected.
- **`dangerouslySetInnerHTML` for map attribution** (`web/.../LocationPicker.tsx:64`): strings
  are static vendor HTML, no user input. Anti-pattern, not a live XSS. Direction, not a plan.
- **Caret (`^`) dependency ranges** (`web/package.json`): standard; acceptable once CI tests
  exist (004). Not a finding.
- **`console.warn(err)` in SpotMap** (`SpotMap.tsx:185,197`): no token in the error object.
  Log-hygiene nit, not a leak. Rejected.
- **SpotMap cluster `active` stale-closure** (`SpotMap.tsx:393-417`): `renderCluster` captures
  `sel`/`focus` at call time; a selection change during async `getClusterLeaves()` can briefly
  show a stale cluster highlight, but self-heals on the next `updateMarkers()` (map move/data).
  Minor cosmetic, self-correcting — not worth a plan.
- **Separate `AGENTS.md`/`CLAUDE.md`**: a minimal `AGENTS.md` was created during 001 apply
  (repo had neither). Resolved, not pending.

### Rejected in pass 2 (2026-09-17)

- **Upload extension trusts the client filename** (`SupabaseStorageService.java:56-63`,
  `UploadsController.java:41`): the stored object key takes its extension verbatim from
  `getOriginalFilename()`. Downgraded to not-worth-a-plan: `UploadsController` allowlists
  the mime type and `PutObjectRequest` sets `contentType` from it, so a `.svg`/`.html`
  extension is still served as an allowlisted image type and won't execute. The
  `dot > slash` guard also rules out path traversal in the extension. Worth a 3-line
  tidy-up (derive the extension from the validated mime only, ignore the filename) if
  someone is in the file anyway — not worth its own PR.
- **`AdminService.listSubmissions()` loads all rows**: correct — it is the admin queue and
  genuinely needs every submission. Not the same finding as D6.

- **Split the Supabase S3 access key from the secret key** (security): `deploy-api.yml:44-45`

## Before merging this branch

Plan 032 ships the HttpOnly refresh cookie. `master` carried a `## Held back` section explaining
why it was kept off; merging this branch is what retires that, and the prerequisite it named is
**not optional**:

- Add a Firebase Hosting rewrite proxying `/api/**` to the `gemspot-api` Cloud Run service and
  repoint `VITE_API_URL` at `https://gemspot.web.app/api` — then ADR 0006's `SameSite=Lax`
  default is correct and nothing else changes. This is the intended path.
- Or set `AUTH_COOKIE_SAMESITE=None`, accepting a third-party cookie that Safari blocks outright
  and Firefox partitions.

`gemspot.web.app` and `*.run.app` are both Public Suffix List entries, so without one of those
two acts the cookie is third-party, `SameSite=Lax` suppresses it, and the result is a broken
login rather than a hardened one. A push to `master` deploys, so the act comes first.
