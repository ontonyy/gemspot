## Findings considered and rejected

- **JWT tokens in `localStorage`** (`web/src/shared/store/authStore.ts`): deliberate SPA choice
  (15m access TTL + server-side refresh-reuse detection). Known trade-off, documented in
  `OBSERVABILITY.md`. Not a bug. See Direction options.
- **`/auth/email/verify` public**: by design — the UUID token *is* the authority. Not a finding.
- **OAuth tokens verified via outbound RestClient to Google/Facebook** (`AuthService.java`):
  standard provider verification, not SSRF. Not a finding.
- **`rejectSubmission()` lacks `@Transactional`** (`AdminService.java:173`) while
  `approveSubmission()` has it: **rejected** — reject is a single `save()` (already transactional
  at the repository boundary); the asymmetry is necessary (approve is multi-write), not a defect.
- **Mutable non-volatile `RestClient` field** (`AuthService.java:50`): the setter is a
  test-only seam and `RestClient` is thread-safe; no realistic production race. Rejected.
- **`dangerouslySetInnerHTML` for map attribution** (`web/.../LocationPicker.tsx:64`): strings
  are static vendor HTML, no user input. Anti-pattern, not a live XSS. Direction, not a plan.
- **Caret (`^`) dependency ranges** (`web/package.json`): standard; acceptable once CI tests
  exist (004). Not a finding.
- **`console.warn(err)` in SpotMap** (`SpotMap.tsx:185,197`): no token in the error object.
  Log-hygiene nit, not a leak. Rejected.
- **SpotMap cluster `active` stale-closure** (`SpotMap.tsx:393-417`): `renderCluster` captures
  `sel`/`focus` at call time; a selection change during async `getClusterLeaves()` can briefly
  show a stale cluster highlight, but self-heals on the next `updateMarkers()` (map move/data).
  Minor cosmetic, self-correcting — not worth a plan.
- **Separate `AGENTS.md`/`CLAUDE.md`**: a minimal `AGENTS.md` was created during 001 apply
  (repo had neither). Resolved, not pending.

## Direction options (maintainer's call — not bugs)

- **Token storage hardening**: move refresh token to an HttpOnly + SameSite cookie and
  keep only the short-lived access token in memory. Removes the localStorage XSS surface
  entirely. Trade-off: backend must set/read cookies and CORS `credentials` is already on,
  but it changes the auth seam in `web/src/shared/api` and `SecurityConfig`. Non-trivial;
  weigh against current short-TTL mitigation.
- **Deploy-target source of truth**: `api/README.md` says Cloud Run (`deploy-api.yml`,
  service `gemspot-api`) while the audit also saw `https://gemspot-api.onrender.com`.
  One is stale. Resolve before `RUNBOOK.md` pins a live URL (plan 001 flags this, does not
  assert it).
- **ADR for monorepo doc layout**: a single repo-root `docs/service-context/` covering two
  deployables (web + api) vs. per-package dirs. Plan 001 takes the root-level approach with
  a `WEB.md` for the frontend; if you prefer per-package, capture it as ADR 0003 first.
- **Split the Supabase S3 access key from the secret key** (security): `deploy-api.yml:44-45`
  notes the access key currently *equals* the secret key and is stored as a GH secret. Rotate
  to a distinct access/secret pair. Ops/config change (no source), not a code plan — no secret
  values are reproduced here; do it in Secret Manager + GH settings.
- **Admin route guard renders before auth hydration** (`web/.../pages/admin/AdminLayout.tsx:19-20`):
  on a cold load an admin can be bounced to `/auth` before the store hydrates, then must
  re-navigate. UX flicker, not an access bypass (no unauthorized data shown). Gate on a
  "hydrated" flag if it annoys users. Maintainer's call.
